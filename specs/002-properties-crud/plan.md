# Implementation Plan: Properties Register

**Branch**: `002-properties-crud` | **Date**: 2026-08-30 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/002-properties-crud/spec.md`

## Summary

Build the properties register: a paged, searchable, filterable Arabic list of properties
with add, modify, archive, restore, and a per-property detail screen. Identity is a
never-reused reference code, generated by the database and overridable by administrators
alone; names may repeat. Administrators additionally maintain the two lookup lists the
property form draws from (types and areas) and define custom property fields of four
types, any free-text one of which may be marked sensitive and is then envelope-encrypted
and withheld from every search. An advanced search filters on the non-sensitive custom
fields. Every write lands in the append-only audit log in the same transaction.

The approach adds one Go package for the domain, one for the envelope crypto that
Principle VII now requires, seven forward-only migrations, twenty OpenAPI operations across twelve paths, and one
Angular feature area plus three administrator screens under the existing Settings shell.
No new third-party dependency is introduced: AES-256-GCM comes from the Go standard
library, and everything else is already in the tree from feature 001.

## Technical Context

**Language/Version**: Go 1.27 (`api/`), TypeScript 5.9 on Angular 22.1 (`web/`)

**Primary Dependencies**: `jackc/pgx/v5` (database), `pressly/goose/v3` (migrations),
`oapi-codegen` (server interface), `@openapitools/openapi-generator-cli`
(`typescript-angular` client), `crypto/aes` + `crypto/cipher` from the Go standard library
for AES-256-GCM. **No new dependency is added by this feature.**

**Storage**: PostgreSQL 17, two roles — `pms_owner` runs migrations, `pms_app` is the
runtime role and holds `SELECT, INSERT` only on `audit_log`.

**Testing**: Manual, per Constitution V, driven by `quickstart.md`. Two narrow Go unit
test files are written anyway because the logic is genuinely tricky and invisible on
screen: the envelope seal/open round trip including tag-tamper rejection, and the
reference-code generator under a collision with an administrator override.

**Target Platform**: Local development only. TLS on both listeners
(`https://localhost:4200`, `https://localhost:8443`).

**Project Type**: Web application in a monorepo — `web/` (Angular) and `api/` (Go).

**Performance Goals**: First page of the list rendered within 2 s at 500 properties
(SC-003); an advanced search combining a built-in filter and two custom-field filters
answers within 2 s at the same size (SC-008c).

**Constraints**: Arabic-only UI, RTL, logical CSS properties only. Every write and its
audit row share one transaction. Sensitive custom values never leave the database as
plaintext except inside a role-checked handler, and never reach a log. Reference codes are
never reused.

**Scale/Scope**: Hundreds of properties, low tens of custom fields, under ten concurrent
users. 8 user stories, 65 functional requirements, 17 success criteria.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

Derived from `.specify/memory/constitution.md` v1.2.0.

**Initial evaluation — before Phase 0:**

- [x] **I. Authorization** — PASS. Every operation in the contract carries
      `x-required-role`. The three configuration areas (property types, areas, custom
      field definitions) and the reference-code change are `admin`; everything else is
      `manager`, which admin also satisfies. The role is read from the server-verified
      session, never from the request. Default is deny: the router's `authed()` wrapper
      refuses any route without an explicit rule.
- [x] **II. Arabic RTL** — PASS. All new strings are Arabic; all new styling uses logical
      properties, checked by the same grep gate feature 001 uses. The design source
      `Property Management System.html` is a visual reference only; what is taken from it
      (list layout, filter chips, the lookup panel shape, the advanced-search form) is
      named in research.md, and its physical CSS is converted on the way in.
- [x] **III. Contract-First** — PASS. `contracts/openapi.yaml` is written in Phase 1,
      before any handler. The Go server interface and the Angular client are both
      generated from it. No hand-written request or response type.
- [x] **IV. Data Integrity** — PASS. Property → type, property → area, custom value →
      property, and custom value → field definition are all real foreign keys, which is
      the reason this plan rejects a JSONB bag for custom values (see research.md, D-002).
      Six forward-only migrations. No money in this feature. All timestamps `timestamptz`
      in UTC.
- [x] **V. Manual Verification** — PASS. `quickstart.md` carries the full procedure,
      including section G, where a manager is refused each of the four configuration
      actions — the manager-denied-configuration step this principle requires.
- [x] **VI. Simplicity** — PASS with a recorded note. The feature is large, but its size
      comes from the specification, not from the plan: every part traces to a clarified
      requirement. See Complexity Tracking for the two places where the plan is more
      elaborate than a first instinct would suggest, and why the simpler option was
      rejected.
- [x] **VII. Encryption** — PASS, and only under v1.2.0. This feature is the reason
      Principle VII was amended on 2026-08-30. Designation is free-text-only, custom-field
      only, fixed once values exist, and carries exclusion from search, sort, filter, and
      report — the four bounds the amendment sets. Envelope encryption is AES-256-GCM with
      a per-value data key wrapped by the environment-supplied KEK; the tag is verified on
      every read; no decrypted value reaches a log, an error body, or an audit row. TLS is
      already on both listeners from feature 001.
- [x] **VIII. Audit** — PASS, but it requires widening the audit table. `audit_log` as
      built in feature 001 can only name an *account* as its target — it has
      `target_account_id` and `target_username_snapshot` and nothing else. Principle VIII
      demands entity type and entity identifier for every business record. Migration 0009
      adds nullable `entity_type` and `entity_id` columns and leaves the account columns
      untouched, so feature 001's rows and queries are unaffected. The append-only
      guarantee is unchanged: `pms_app` still holds `SELECT, INSERT` only.

**Re-evaluation after Phase 1 design**: see [Post-Design Constitution Re-Check](#post-design-constitution-re-check) below.

**Structure Decision**: The existing monorepo is unchanged in shape. This feature adds two
Go packages (`crypto`, `properties`) and one Angular feature area plus three
administrator screens hosted inside the Settings shell built in feature 001. The lookup
panel is written once and instantiated twice, for types and for areas, because they have
identical shape and rules — this is the single reuse the plan permits itself, and it is
reuse of an actual duplicate, not a speculative abstraction.

## Complexity Tracking

> Recorded per Principle VI. Neither entry is a violation; both are places where the
> obvious simpler option was rejected for a stated reason, and saying so here is what the
> principle asks for.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Custom field values stored as rows in three tables rather than one JSONB column on `property` | FR-027f requires a value to refer to its field definition by identity so a rename propagates, and FR-027g requires refusing to delete a field or a choice while values reference it. Both are referential questions. | A JSONB bag cannot carry a foreign key. Enforcing "this choice is still in use" would move from the database to application code, which Principle IV forbids: relationships MUST be real foreign keys and orphans MUST be impossible at the schema level, not merely unlikely. |
| A separate `PATCH /properties/{id}/code` operation instead of accepting `code` inside the property update body | FR-017c gives administrators alone the right to set a reference code, while both roles may edit every other property field. | Accepting `code` in the shared update body would make one operation's authorization depend on which fields the body happens to contain — exactly the conditional, body-derived permission check Principle I rules out. A separate operation carries one flat `x-required-role: admin`. |

## Post-Design Constitution Re-Check

Re-run after `research.md`, `data-model.md`, `contracts/openapi.yaml`, and `quickstart.md`
were written. All eight gates still PASS. Three things the design surfaced that the
initial check had not:

1. **Gate VIII needed a schema change, not just a code change.** Recorded above and
   carried into migration 0009. Without it the audit rows for this feature could not name
   what they changed, and Principle VIII would have failed silently — which is precisely
   the failure mode the Governance section warns about.
2. **Gate VII needed the advanced search to know about designation.** The contract omits
   sensitive fields from the advanced-search filter list at the schema level rather than
   filtering them out in the UI, so a client that ignores the UI still cannot search them.
   Enforcement is on the server (research.md, D-006).
3. **Gate I needed the code-change split.** Recorded in Complexity Tracking above.
